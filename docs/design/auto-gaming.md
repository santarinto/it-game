# Автогейминг и симуляция без графики в IT-Director (ITGAME-206)

Ретроспектива и инвентарь инструментов для автономной игры, балансировочных прогонов и тестирования без графического интерфейса.

---

## 1. Инвентарь инструментов

В проекте исторически сложилось 5 уровней симуляции и взаимодействия без участия человека:

```
+--------------------------------------------------------------------------+
| 1. Headless Engine: make sim (cmd/sim)                                  |
|    - Чистый Go, без сети и браузера, прямое управление Game              |
|    - Скорость: ~10,000 дней/сек                                          |
+--------------------------------------------------------------------------+
| 2. Replay Engine: make replay (cmd/replay)                              |
|    - Воспроизведение сид + журнал клиентских команд → побайтовый сейв    |
+--------------------------------------------------------------------------+
| 3. WebSocket Bridge: /ws/agent & /api/debug/* (internal/ws)             |
|    - Headless WS-клиент или наблюдатель к живой сессии                   |
|    - Управление состоянием (сценарии, патчи, шаги тиков)                 |
+--------------------------------------------------------------------------+
| 4. Network Bots: load-bots.mjs (client/scripts)                         |
|    - Множество параллельных ботов через реальный /ws                     |
|    - Нагрузка стейджа, замер p95 тика и сейва, watchdog на паузах       |
+--------------------------------------------------------------------------+
| 5. Headless Browser Facade: window.itd (client/src/debug/agentApi.ts)    |
|    - Консольный API в Phaser/Canvas, виртуальный хит-тест, линтер верстки|
+--------------------------------------------------------------------------+
```

### 1.1 `make sim` (`server/cmd/sim`)
* **Назначение**: Массовые балансировочные прогоны (300 сидов × 30 дней) для калибровки цен, штрафов аудита, частоты поломок и шансов выживания.
* **Политики**:
  - `greedy` — жадный наём, покупка ПК, апгрейды рабочих мест, мгновенный ремонт и чистка.
  - `idle` — полное бездействие (базовая скорость гибели офиса).
  - `random` — хаотичные случайные клики.
  - `handsoff` — замер цены отсутствия игрока: играет до 4 сотрудников, затем прекращает ручные клики.
  - `delegate` — замер цены админа: нанимает админа в выросший офис при первой финансовой возможности.
  - `expand` — агрессивное расширение: покупка новых офисов по мере заполнения существующих (до 60 дней).
* **Флаги телеметрии**:
  - `--events-text`: расшифровка названий выпавших событий.
  - `--audit-stats`: статистика банкротств в день аудита.
  - `--event-stats`: распределение случайных поломок, вспышек и событий пула относительно суточного бюджета событий.
  - `--answer-raise` (`accept`/`decline`): политика ответов на просьбы о повышении.
  - `--answer-leave` (`release`/`keep`/`by-hour`): политика ответов на уход пораньше.

### 1.2 `make replay` (`server/cmd/replay`)
* **Назначение**: Детерминированное воспроизведение реальной партии по журналу входов.
* **Механика**:
  - Читает лог `party.jsonl` (сид, команды игрока с тиками, внешние вмешательства).
  - Прокручивает ядро игры шаг за шагом.
  - Сверяет финальный сейв реплея со слепком живой сессии байт-в-байт. Используется в автотесте `qa:journal`.

### 1.3 WS-мост `/ws/agent` и `/api/debug/*`
* **Назначение**: Программное управление сессией без подъёма Chromium.
* **Эндпоинты**:
  - `GET /ws/agent?sid=...` — WebSocket-канал с ролью `owner` (управление) или `observer` (наблюдение за живой партией игрока).
  - `GET /api/debug/fixtures` — список встроенных JSON-фикстур (`fresh`, `admin_dept`, `worn_pcs` и др.).
  - `GET /api/debug/state?sid=...` — выгрузка полного снапшота и сейва текущей партии.
  - `POST /api/debug/state` — единая точка управления состоянием:
    - загрузка сценария/фикстуры: `{"sid": "...", "scenario": "admin_dept"}`;
    - восстановление из слепка (restore): `{"sid": "...", "state": {...}}`;
    - точечный патч параметров: `{"sid": "...", "money": 5000, "day": 10}`.
  - `POST /api/debug/advance` — мгновенная офлайн-промотка времени без реального ожидания: `{"sid": "...", "days": 3}` (до 90 дней) или `{"ticks": 500}` (до 10,000 тиков).
  - `GET /api/debug/journal?sid=...` — выгрузка журнала действий в JSONL для скармливания в `cmd/replay`.
  - `GET /api/debug/events?sid=...` и `GET /api/debug/ledger?sid=...` — инспекция очереди событий и суточного финансового леджера.
  - `POST /api/cheat/money` — быстрое начисление средств на localhost (`server/cmd/server/main.go`, вне префикса `/debug/`).

### 1.4 Нагрузочные боты `client/scripts/load-bots.mjs`
* **Назначение**: Нагрузочное тестирование стенда/стейджа десятками и сотнями одновременных партий по WebSocket.
* **Механика**:
  - Каждый бот поднимает отдельное WebSocket-соединение со своим `sid` (`loadbot-<run>-<i>-<gen>`) с параметром `client=bot`.
  - Цикл принятия решений по входящим `state`: закрытие дня (`next_day`), выбор опций событий, клики чистки вируса и ремонта, покупка ПК и найм.
  - Сторож `watchdog`: отслеживает паузу отчёта дня (когда тики перестают приходить) и форсирует принятие решений, предотвращая зависание ботов.

### 1.5 Headless Browser Facade: `window.itd` (`client/src/debug/agentApi.ts`)
* **Назначение**: Консольный фасад в браузере (доступен в dev-сборке и в проде с параметром `?debug=1`), позволяющий агентам и Puppeteer управлять игрой на уровне Phaser/Canvas без скриншотов и ненадежного DOM-ввода.
* **Ключевой API**:
  - **Чтение состояния**:
    - `itd.state()` — полный слепок состояния клиента (`phase`, `room`, `money`, `day`, `staff`, `menuReady`).
    - `itd.nodes()` / `itd.ids()` — список интерактивных игровых объектов с их стабильными строковыми ID, сценой и флагами `active`, `disabled`, `title`.
    - `itd.screen(opts)` — визуальный слепок экрана и видимых интерактивных узлов в заданной рамке пикселей.
  - **Действия и команды**:
    - `itd.cmd(type, office, extra)` — отправка серверной команды с ожиданием квитанции от сервера (`sendWithReceipt`).
    - `itd.click(id)` / `itd.tap(id)` — клики по координатам центра интерактивного объекта с хит-тестом (`itd.hit(id)`) и проверкой перекрытия (`itd.stack(id)`).
    - `itd.wait(predicate, timeoutMs)` — ожидание выполнения условия с автоматическим прогревом скрытой вкладки (`warmIfHidden()`).
    - `itd.away(sec, opts)` / `itd.offline()` — симуляция ухода игрока и проверка догона оффлайн-времени.
  - **Линтер верстки**:
    - `itd.overlaps(opts)` — поиск взаимного перекрытия интерактивных кнопок и панелей (защита от недоступных элементов).
    - `itd.offscreen()` — поиск объектов, вышедших за границы холста.
    - `itd.tiny()` и `itd.contrast()` — поиск слишком мелких интерактивных зон и текста с низкой контрастностью.
  - **Координация ввода и агентские диалоги**:
    - `itd.claim` — владение вводом для предотвращения гонок между человеком и агентом.
    - `itd.ask` — проведение структурированных интерактивных опросов прямо в игровом интерфейсе.
    - `itd.trace()` — трассировка последовательности вызовов и реакции компонентов.

## 2. Ретроспектива: где спотыкались агенты

Анализ закрытых задач балансировки, нагрузок и багов (`ITGAME-135`, `ITGAME-156`, `ITGAME-173`, `ITGAME-193`, `ITGAME-196`):

1. **Зависание ботов на фазе отчёта дня (`ITGAME-193`)**:
   - *Проблема*: Сервер останавливает тики при наступлении 19:00 (`PhaseDayReport`). Бот, ожидавший следующего снапшота для реакции, засыпал навсегда. Команда, отправленная в последний момент дня, возвращала `wrong_phase`, сбивая очередь команд.
   - *Решение*: Внедрение сторожа (`watchdog`), который раз в секунду опрашивает последний снапшот и при тишине >1.5с отправляет `next_day`.

2. **Рассинхрон комментариев и метрик исходов в `sim` (`ITGAME-173`)**:
   - *Проблема*: В документации и комментариях кода исходы перечислялись как `(bankrupt | victory | time_up)`, в то время как движок возвращал также `deadlock` (все места сломаны/заражены без денег) и `timeout` (достигнут лимит дней симулятора).
   - *Решение*: Нормализация пяти статусов завершения партии и фиксация единого стандарта описания в `gdd.md` и `development.md`.

3. **Отставание политик `sim` от новых механик (`ITGAME-135`, `ITGAME-144`, `ITGAME-197`)**:
   - *Проблема*: При добавлении износа ПК (`ITGAME-135`), смен админов (`ITGAME-144`), ролей сотрудников (`ITGAME-197`) политики `greedy` и `delegate` не обновлялись автоматически. Например, `server/cmd/sim/policy.go` проверяет только `o.Admin != ""` и не нанимает 2-ю и 3-ю смену админов (`o.NextAdminShift()`), а при заполнении офиса ломается балансировочный расчёт ценности расширения.
   - *Вывод*: Любая новая игровая механика требует явного расширения интерфейса политик `sim`.

4. **Ручное сведение результатов и отсутствие авторегрессии**:
   - *Проблема*: Результаты прогонов `make sim` выводятся в CSV или stderr. Агенту приходится писать временные awk/python/node однострочники, чтобы посчитать медиану и проценты банкротств, а затем вручную сверять их с таблицей в `gdd.md`.
   - *Вывод*: Необходима персистентная база прогонов с автоматическим сравнением дельты (задача `ITGAME-126`).

## 3. Разрывы и чего не хватает

1. **Headless-запуск фикстур одной командой**:
   - Сейчас агент вынужден запускать полноценный Puppeteer (`qa:admins`, `qa:pc`), чтобы проверить поведение на фикстуре `admin_dept.json`, либо вручную слать HTTP-запросы в `/api/debug/state` + `/api/debug/advance`.
   - *Потребность*: Прямая поддержка прогона фикстур в headless CLI — либо через аргумент `make sim ARGS="--scenario admin_dept --days 10"`, либо через отдельную утилиту runner'а фикстур с JSON-отчётом.

2. **Учёт очков действий (`actionPoints`) в `sim`**:
   - В игре игрок ограничен 8 очками действий в день (`ITGAME-127`). Движок `game.Game` возвращает ошибку `ErrNoActionPoints` при исчерпании очков. Однако политика `greedy` в `sim` не планирует суточный бюджет AP: она пытается спамить кликами ремонта и антивируса вслепую (клики молча отбрасываются), не приоритизирует критические поломки перед рутиной и не использует вызов мастера (`CmdCallMaster`), когда AP закончились.
   - *Потребность*: Внедрение бюджетирования AP в эвристики `greedy` и `delegate`.

3. **Связь политик с новыми отделами и механиками**:
   - Включение в `cmd/sim/policy.go` поддержки найма всех 3 смен админов (`ITGAME-144`).
   - Подготовка симулятора к отделу продаж (`ITGAME-200`): продажа услуг через продавцов, командировки, ноутбуки.

4. **CLI-инструмент записи и реплея сценариев ботов**:
   - Утилита для запуска одиночного бота по `/ws` с сохранением полного лога тиков и команд в файл для быстрой отладки краевых ситуаций.
