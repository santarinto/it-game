## 1. Контекст и цели задачи

### 1.1 Проблема
Сейчас мета-прогресс живёт **полностью на клиенте** в `localStorage` ([`client/src/meta.ts`](../../client/src/meta.ts)):
- Ключи `itd.meta_stats` и `itd.meta_achievements` хранятся в браузере игрока.
- Достижения и статистика проверяются клиентом по входящим сообщениям `StateMessage`, `VictoryMessage` и `GameOverMessage`.
- Любой игрок может в DevTools выполнить `localStorage.setItem('itd.meta_achievements', ...)` или `window.itd.unlockAchievement(...)`, получив все ачивки и фальшивые рекорды баланса.
- При смене браузера или очистке кэша все достижения и статистика безвозвратно теряются.

### 1.2 Цель
1. Сделать сервер и базу данных PostgreSQL **источником истины** для мета-прогресса (достижений, рекордов и статистики побед/поражений).
2. Привязать мета-прогресс к браузеру/игроку через стабильный ключ `player` (из `localStorage`).
3. Сохранить принцип **автономности и необязательности БД** (`ITGAME-190`): при недоступности PostgreSQL или игре офлайн клиент плавно переключается на локальный кэш без ошибок.

## 2. Идентификатор игрока (`player_id`)

В игре намеренно нет регистрации и паролей. Сессии `sid` живут одну партию (после рестарта или победы клиент создаёт новый `sid`).

Для постоянного связывания партий одного игрока:
1. **Клиентский ключ**:
   - Клиент генерирует случайный идентификатор игрока в `localStorage` по ключу `itd.player`:
     `p_<uuid>` (например, `p_a1b2c3d4-e5f6-7890-abcd-ef1234567890`).
   - Если ключ уже есть в `localStorage`, клиент читает его; если нет — создаёт один раз и сохраняет на клиенте навсегда.
2. **Передача на сервер**:
   - Параметр `player` передаётся во все WebSocket-подключения:
     - Основная сессия игры: `/ws?difficulty=...&sid=...&client=desktop&player=p_...`
     - Сводка для меню (peek): `/ws?peek=1&player=p_...` (с `sid` или без него).
3. **Хранение в БД**:
   - В таблицах `parties` и `player_meta` сохраняется строка `player` (до 64 символов). Поскольку это случайный сгенерированный UUID браузера, он не содержит персональных данных (PII).

## 3. Схема данных (миграция `0004_player_meta.sql`)

Схема логически встаёт рядом с `0003_parties.sql`:

```sql
-- 1. Добавление ссылки на игрока в таблицу parties
ALTER TABLE parties ADD COLUMN IF NOT EXISTS player text NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS parties_player ON parties (player) WHERE player <> '';

-- 2. Пересоздание представления party_status (включение новой колонки player)
CREATE OR REPLACE VIEW party_status AS
SELECT p.*,
       CASE WHEN p.outcome IS NOT NULL THEN p.outcome
            WHEN p.expires_at < now() THEN 'dropped'
            ELSE 'running' END AS status
FROM parties p;

-- 3. Таблица мета-прогресса игрока: агрегаты и ачивки
CREATE TABLE IF NOT EXISTS player_meta (
    player        text PRIMARY KEY,             -- стабильный player_id из localStorage
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now(),
    total_runs    int    NOT NULL DEFAULT 0,    -- число завершённых партий
    total_wins    int    NOT NULL DEFAULT 0,    -- число побед
    total_losses  int    NOT NULL DEFAULT 0,    -- число поражений
    peak_balance  bigint NOT NULL DEFAULT 0,    -- максимальный баланс за всю историю
    peak_day      int    NOT NULL DEFAULT 0,    -- максимальный день выживания
    -- Детальная статистика по сложностям (зеркало MetaStats.byDifficulty в TS):
    -- {"easy": {"runs":0, "wins":0, "bankruptcies":0, "timeUps":0, "bestDay":0, "bestWinDay":null, "bestBalance":0}, ...}
    stats         jsonb  NOT NULL DEFAULT '{}',
    -- Полученные достижения (зеркало Record<string, AchievementState> в TS):
    -- {"first_hire": {"id": "first_hire", "unlockedAt": 1730290000000}, ...}
    achievements  jsonb  NOT NULL DEFAULT '{}'
);

CREATE INDEX IF NOT EXISTS player_meta_updated ON player_meta (updated_at DESC);
```

### Преимущества схемы:
- Хранение `stats` и `achievements` в виде компактного `jsonb` исключает сложный relational-overhead на 12 ачивок, идеально ложится на TypeScript-интерфейсы `MetaStats` и `AchievementState`, и читается/пишется одним запросом за 0.5 мс.
- Колонка `player` в `parties` позволяет при необходимости пересчитать мета-прогресс игрока «с нуля» по истории его сыгранных партий.

## 4. Расчёт достижений и статистики на сервере

Все 12 достижений полностью проверяются серверным состоянием `game.Game`:

| ID достижения | Название | Условие в Go (`game.Game`) | Триггер проверки |
|---|---|---|---|
| `first_hire` | Первые кадры | `g.TotalEmployees() > 0` | Найм сотрудника (`CmdHire`), выбор в `EventStar` |
| `first_day` | Первый рабочий день | `g.Day > 1` | Закрытие 1-го дня (`Tick` / отчёт дня) |
| `coffee_break` | Кофейная пауза | Наличие кофемашины в любом офисе (`o.CoffeeMachine`) | Покупка аменити (`CmdBuyCoffee`) |
| `star_hunter` | Охотник за звёздами | Есть хотя бы один сотрудник со `Star = true` | Найм с шансом звезды (`CmdHire`), выбор в `EventStar` |
| `survivor_10` | 10 дней без банкротства | `g.Day > 10` | Закрытие дня (`g.Day > 10`) |
| `three_offices` | Корпорация | Все 3 офиса разблокированы (`g.Offices[i].Unlocked`) | Покупка офиса (`CmdBuyOffice`) |
| `full_staff` | Полный штат | `g.TotalEmployees() >= 36` | Найм сотрудника (`CmdHire`, `EventStar`) |
| `core_max` | Ядро системы | `g.CoreLevel >= len(g.Config().CoreLevels)` | Апгрейд Core (`CmdUpgradeCore`) |
| `network_36` | 36/36 в сети | `g.TotalEmployees() == 36 && g.Network().CoreUsed >= 36` | Тик сети / переподключение / апгрейды |
| `millionaire` | Первый миллион | `g.Money >= 1_000_000` | Любое изменение баланса (тик дохода, продажа) |
| `clean_win` | Победа без аменити | Победа и во всех офисах нет кулеров, холодильников и кофемашин | Момент победы (`PhaseWon`) |
| `hardcore_win` | Хардкорный директор | Победа на сложности `hardcore` | Момент победы (`PhaseWon`) |

### Предотвращение дублирования и спама тостами:
1. **Кэш открытых ачивок в акторе**:
   - При старте сессии актор загружает список уже открытых ачивок игрока `player` из `player_meta`.
   - В памяти актора держится `unlocked map[string]bool`. Проверка условий ачивок выполняется только для ещё не открытых.
   - Новое достижение отправляет клиенту отдельное сообщение протокола:
     ```json
     {
       "type": "achievement_unlocked",
       "id": "coffee_break",
       "unlockedAt": 1730290123456
     }
     ```
2. **Фильтрация на клиенте**:
   - Клиент в `HUDScene` перед показом всплывающего тоста и звука `playSfx('confirmation')` сверяется с локальным состоянием: если ачивка уже числилась открытой, повторный показ и звук подавляются.

## 5. Доставка мета-прогресса в клиент

### 5.1 Меню (`MenuScene`) и безусловный `peek`
Сейчас в `MenuScene.ts` `peekSave` вызывается только при `this.hadSave`. Это приводило бы к тому, что игрок без активной партии (первый вход, после победы или «Сдаться») не получал бы мета-прогресс.

**Архитектурное решение**:
1. `MenuScene` подключается к `/ws?peek=1&player=p_...&sid=...` **безусловно** при старте экрана меню.
2. В `server/internal/ws/peek.go` метод `servePeek` принимает параметры `sid` и `player`:
   - Если `sid` пуст или сейва нет, сервер возвращает `exists: false, alive: false`, **но** если передан `player`, сервер подгружает из БД `player_meta` и отдаёт поле `meta` в `save_summary`:
     ```json
     {
       "type": "save_summary",
       "exists": false,
       "alive": false,
       "day": 0,
       "money": 0,
       "meta": {
         "stats": { ... },
         "achievements": {
           "first_hire": { "id": "first_hire", "unlockedAt": 1730290000000 }
         }
       }
     }
     ```
3. Клиент сохраняет полученные данные в локальный кэш, и меню сразу отображает корректные счетчики *«Партий: X · Побед: Y · Достижения: N/12»*.

### 5.2 Сессия игры (`HUDScene`)
- При подключении к игровой сессии `/ws?...&player=p_...` сервер отправляет клиенту отдельное WS-сообщение типа `meta` со слепком статистики и открытых ачивок.
- В ходе игры при выполнении условий новых достижений сервер присылает сообщение `achievement_unlocked`.

### 5.3 Безопасность и защита от накруток в DevTools
- Клиентский `localStorage` больше не является источником истины. Любые попытки вызвать локальный `unlockAchievement(...)` или вручную изменить `localStorage` будут перезаписаны сервером при следующем обмене сообщениями.

## 6. Миграция существующих данных игроков (First-Run Seed)

Чтобы живые игроки при выкатке релиза не потеряли уже заработанные достижения и статистику из `localStorage`:
1. При первом подключении к `/ws` или `peek` клиент передаёт флаг наличия локальных данных.
2. Если в `player_meta` для данного `player` запись отсутствует (первый визит), сервер выполняет **мягкую инициализацию (seed)**: принимает клиентские ачивки и рекорды, валидирует их по списку 12 известных ключей и сохраняет как стартовую запись в `player_meta`.
3. При повторных подключениях источником истины является исключительно база данных сервера.

## 7. Отказоустойчивость, работа без БД и QA-инструменты

1. **Правило `ITGAME-190` (работа без БД)**:
   - В `ws.Handler` доступ к чтению `player_meta` защищён коротким таймаутом (например, 500 мс).
   - Если PostgreSQL лежит, не настроен (`DATABASE_URL=""`) или запрос завершился ошибкой:
     - Сервер отдаёт `meta: null` / опускает поле `meta`.
     - Клиент прозрачно использует локальный кэш из `localStorage`.
     - Игра продолжает работать без ошибок и задержек.
2. **Поддержка `window.itd.resetMeta()`**:
   - Вызов `itd.resetMeta()` в консоли агента или тестах очищает `localStorage` и **генерирует новый случайный `player_id`**.
   - Это гарантирует, что старые данные игрока не «воскреснут» с сервера при следующем запросе, обеспечивая чистую изоляцию в тестах (например, в `qa-itgame10.mjs`).
3. **Партии ботов (`load-bots.mjs`)**:
   - Боты подключаются с `client=bot`.
   - Записи ботов игнорируются для `player_meta`, не создавая мусорных строк в базе.

## 8. Вопросы для согласования с владельцем (Decision Points)

1. **Формат и генерация `player_id`**:
   - Одобряется ли формат `p_<uuid>` в `localStorage['itd.player']`?
2. **Мягкая миграция существующих ачивок (First-Run Seed)**:
   - Согласовано ли первичное сохранение локальных ачивок игрока в БД при первом старте, чтобы не сбрасывать текущий прогресс живых игроков?
3. **Хранение `stats` и `achievements` в JSONB**:
   - Утверждаем ли компактную схему с `jsonb` в `player_meta` (зеркало TypeScript-интерфейсов `MetaStats` и `AchievementState`)?
