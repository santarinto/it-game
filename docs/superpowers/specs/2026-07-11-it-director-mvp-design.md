# IT Director Web Game — дизайн первой итерации (MVP)

Дата: 2026-07-11
Статус: утверждён к реализации

## Контекст и цель

Форк старой web-игры Intel «IT Manager 3: Unseen Forces» в pixel style.
Кликер/симулятор развития IT-компании: интерфейс крутится вокруг комнат
(офис, серверная), между которыми игрок переключается.

Главная цель проекта — **изучение Go**: вся игровая логика живёт на сервере.

Геймдизайн ведётся в отдельном живом документе: [`docs/design/gdd.md`](../../design/gdd.md).
Правило процесса: перед каждой итерацией сначала правится GDD, потом код.

## Рамки MVP

В MVP входит только базовый цикл (валюта — доллар США):

- деньги → покупка ПК в офис → найм сотрудника за ПК → сотрудник производит
  единицы работы, конвертируемые в $ каждый тик;
- роутер (покупается отдельно) подключает рабочие места к сети;
- серверы (покупаются отдельно) — мультипликатор выработки подключённых мест;
- две комнаты (офис, серверная) с переключением;
- **без сохранений**: одна игра живёт в памяти сервера на время WebSocket-сессии;
- **без аккаунтов**;
- арт — готовые CC0-паки (Kenney.nl, itch.io).

Не входит (бэклог в GDD): поломки/ремонт, оффлайн-прогресс, апгрейды офиса,
типы сотрудников, события, персистентность, аккаунты.

## Архитектура

Монорепозиторий:

```
it-director-web-game/
├── server/                  # Go
│   ├── cmd/server/main.go
│   └── internal/
│       ├── game/            # чистая доменная логика (без сети и JSON-тегов протокола)
│       └── ws/              # WebSocket-сессии, протокол
├── client/                  # Phaser 3 + TypeScript + Vite
└── docs/
    ├── design/gdd.md        # живой геймдизайн-документ
    └── superpowers/specs/   # техспеки итераций
```

Ключевое разделение: пакет `game` не знает ни про WebSocket, ни про протокол —
только состояние, команды и тик. Полностью юнит-тестируем.

Dev-режим: Vite dev server проксирует `/ws` на Go-сервер.
Prod: Go отдаёт собранную статику клиента сам.

## Модель конкурентности (ядро Go-обучения)

На каждое WS-подключение создаётся своя игра и одна горутина-«актор»:

```go
select {
case cmd := <-commands: // команда игрока → валидация → применение → пуш стейта
case <-ticker.C:        // 1 тик/сек → начисление дохода → пуш стейта
case <-ctx.Done():      // отключение клиента → остановка игры
}
```

Состоянием владеет ровно одна горутина — мьютексы не нужны.
Разрыв соединения = смерть игры (сохранений в MVP нет).

## Игровые правила MVP

Состояние: деньги ($); 9 слотов офиса под ПК; специальный слот роутера
(типы слотов не взаимозаменяемы: ПК туда не ставится, роутер — только туда);
3 слота серверной под стойки; ПК (свободен/занят сотрудником); сотрудники;
роутер (нет / тир 1 / тир 2); серверы.

- **Старт:** 1 установленный ПК, $600; роутера, серверов и сотрудников нет.
- **Купить ПК** — есть свободный слот офиса и деньги.
- **Нанять сотрудника** — есть ПК без сотрудника и деньги.
- **Купить/улучшить роутер** — покупает следующий тир (нет → тир 1 → тир 2);
  выше тира 2 — ошибка `router_maxed`.
- **Купить сервер** — есть свободный слот серверной и деньги.
- **Сеть:** роутер даёт N портов (тир 1 — 4, тир 2 — 9). К сети автоматически
  подключены первые N занятых рабочих мест.
- **Каждый тик (1 сек):**
  `деньги += Σ по сотрудникам: базовая_выработка × (подключён ? множитель : 1)`,
  где `множитель = 1.5 + 0.5 × число_серверов` (потолок ×3.0 при 3 серверах).
  Серверы без роутера не дают ничего.

Весь баланс — в одном конфиг-файле сервера (цены, выработка, порты, множители,
стартовые значения). Актуальные числа и обоснование — в GDD, раздел «Экономика».
Черновик: старт $600; ПК $500; найм $300; роутер $800/$2500; сервер $2000;
базовая выработка $10/тик.

## Протокол (JSON поверх WebSocket)

Библиотека: `github.com/coder/websocket`.

Клиент → сервер:

```json
{"type": "buy_pc"}
{"type": "hire"}
{"type": "buy_router"}
{"type": "buy_server"}
```

Сервер → клиент:

- `{"type": "state", ...полный снапшот состояния}` — при подключении,
  после каждой команды и каждый тик. Дифы не нужны: состояние крошечное.
  Снапшот включает вычисленные поля для HUD: доход за тик, число портов,
  число подключённых мест, текущий множитель.
- `{"type": "error", "code": "..."}` — коды: `not_enough_money`,
  `no_free_office_slot`, `no_free_rack_slot`, `no_free_pc`, `router_maxed`,
  `unknown_command`.

## Клиент (Phaser 3 + TypeScript + Vite)

Сцены:

- **Boot** — загрузка ассетов;
- **Office** — фон-комната, 9 слотов (пустой → стол с ПК → стол с ПК
  и сотрудником) + слот роутера; подключённые к сети места помечены
  (например, индикатор-лампочка);
- **ServerRoom** — фон, 3 слота под стойки;
- **HUD** (поверх остальных) — деньги, доход за тик, «в сети M из N»,
  кнопки «Купить ПК», «Нанять», «Роутер», «Купить сервер»,
  переключатель Офис ⇄ Серверная.

Клиент без игровой логики: получил снапшот → перерисовал; кнопка → команда.
`pixelArt: true` в конфиге Phaser.

## Обработка ошибок

- Невалидная команда → сервер отвечает `error`, клиент показывает
  всплывающую плашку (например, «Не хватает денег»).
- Разрыв WS → клиент показывает «Соединение потеряно — обнови страницу».

## Тестирование

- `internal/game`: table-driven юнит-тесты всех команд, лимитов и тика — по TDD.
- WS-слой: один интеграционный тест (подключиться, купить ПК, получить стейт).
- Клиент: проверка типов TypeScript + ручная проверка в браузере.
- Конец итерации — плейтест, наблюдения записываются в GDD.

## Порядок работ

1. Скаффолдинг: Go-модуль, Vite+Phaser-клиент, Makefile (`make dev`).
2. Домен `game` в Go по TDD: состояние, 4 команды, тик, сеть/множители,
   конфиг баланса.
3. WS-слой: сессия-актор, протокол, интеграционный тест.
4. Клиент: подключение к WS, HUD с тикающими деньгами.
5. Офис: слоты, покупка ПК, найм, роутер и индикация сети.
6. Серверная: стойки, переключение комнат, эффект множителя.
7. Арт-проход: CC0-ассеты вместо плейсхолдеров.
8. Полировка: плашки ошибок, экран дисконнекта, README, плейтест → заметки в GDD.
